# Mojo 1.0.0

> **This page is the only place in this buch where pre-1.0 syntax is shown.**
> Everything outside `versions/` teaches Mojo 1.x, and only 1.x. The "before"
> blocks below are labelled **pre-1.0** and are kept here solely so you can
> recognise and rename old code. They no longer compile, or they warn. **Never
> copy a "before" block into new code.** The "after" blocks are the 1.x forms.
>
> Every old spelling in the tables is marked either **`REMOVED`** (the spelling
> no longer parses or no longer resolves) or **`DEPRECATED`** (it still compiles
> in 1.0.0 through an alias, but it is not idiomatic and may warn, and it will be
> removed in a future release). No old spelling is ever shown as a valid 1.x
> form.

**Release:** Mojo v1.0.0 — August 11, 2026 (`mojo==1.0.0`). Source:
<https://mojolang.org/releases/v1.0.0/>.

## What 1.0.0 means

### First stable release; semantic versioning begins

1.0.0 is the **first stable release** of Mojo. Before it, the version number
moved through three eras (plain `0.x` in 2023, the bundled MAX CalVer
`24.1`–`25.5` in 2024–2025, and a `0.`-prefixed line `0.25.6`–`0.26.2` in
2025–2026). From 1.0 on, Mojo follows **semantic versioning** for the core
language and the stable parts of the standard library. Source:
<https://mojolang.org/releases/v1.0.0/>.

The official framing for the whole 1.x line, quoted:

> "With Mojo 1.0 we're beginning to define the stability policies for the Mojo
> language and standard library. During the 1.x timeframe, changes should mostly
> be additive. We may still make breaking changes, but they'll be managed with
> care."

> "At this point, most core language features are stable, meaning they won't be
> removed or changed in ways that breaks source compatibility. And we've
> *started* marking standard library APIs as stable, beginning with a
> deliberately small set that we'll grow in subsequent releases."

Read those two sentences carefully, because they set expectations for this whole
chapter: **language features are stable by default in 1.x, standard-library APIs
are not.** The stable stdlib set in 1.0.0 is deliberately small — the
`Deinitable`, `Movable`, `Copyable` and `ImplicitlyCopyable` traits in their
entirety, plus one or more stable APIs each on `Array`, `List`, `Span`,
`String`, `Bool` and `Optional`. Stability is **source-only**: there is no ABI
stability. Sources: <https://mojolang.org/releases/v1.0.0/>;
<https://mojolang.org/docs/api-docs/stability/>.

### 1.0.0 is a migration release

1.0.0 is not primarily about features. It is the point where a long period of
renaming, defaulting and safety-tightening was frozen under a stability
promise, and the official notes say so plainly:

> "We worked hard on getting names, defaults, and safety boundaries right for
> 1.0. That *does* mean you'll find more breaking changes than usual in this
> release. But nearly every breaking change ships with a deprecated alias and a
> compiler fix-it, so migration is mechanical."

So the job for an agent moving 0.x code to 1.x is mostly **mechanical
migration**: rename spellings, write down what used to be inferred, and change
the few APIs that were removed outright. That is what the rest of this page
gives you.

The release notes group the breaking changes under five slogans worth knowing:

- **"One name, and one type, per concept"** — vocabulary consolidation
  (`size` → `length`, `InlineArray` → `Array`, `StringSlice` → `StringSpan`,
  `ImplicitlyDestructible` → `Deinitable`, `read` → `imm`, `Int` =
  `Scalar[DType.int]`).
- **"Explicit over implicit"** — inference rules written down (implicit var-less
  declarations deprecated, `self` must be `Self`, bare `**kwargs` → `var
  **kwargs`, import system overhauled).
- **"Memory safety and pointer unification"** — `Pointer` and `UnsafePointer`
  unified; unsafety marked per operation.
- **"Correct by default, even at the cost of convenience"** — invalid slices
  abort instead of clamping, string iteration yields graphemes, `range()` and
  `size_of()` corrected.
- **"A clearer boundary between Mojo and MAX"** — accelerator APIs moved to the
  `max` package.

Sources for this section: <https://mojolang.org/releases/v1.0.0/>.

## The complete old → new table

Everything below comes from the official 1.0.0 release notes unless a row cites
the beta (`v1.0.0b1`, `v1.0.0b2`) or an earlier release that the change landed
in and 1.0 inherited. The **Status** column is the operative fact: `REMOVED`
means the old form does not work in 1.x; `DEPRECATED` means it still compiles in
1.0.0 but is not idiomatic.

### Language core: functions, declarations, bindings

| OLD (pre-1.0) | NEW (1.x) | STATUS | Official note |
|---------------|-----------|--------|---------------|
| `fn` | `def` | `REMOVED` | `def` is now the standard function keyword. Timeline: v0.26.2 "`fn` is now deprecated and will be removed in a future release"; v1.0.0b1 "Mojo now emits a compiler warning on uses of `fn`; this will become a compilation error in the next release"; **v1.0.0b2 "The legacy `fn` keyword now produces an error instead of a warning. Please move to `def`."** Old code with `fn` does not compile on 1.0.0. |
| `def` that implicitly raised | `def` + `raises` | `REMOVED` (semantics changed) | "`def` functions no longer implicitly raise and now have the same semantics as `fn`: non-raising by default, with explicit `raises` for functions that can throw." (v0.26.2) |
| `let x = ...` | `var x = ...` | `REMOVED` | Removed long before 1.0: "The `let` keyword has been completely removed from the language. We previously removed `let` declarations but still provided an error message to users. Now, it is completely gone from the grammar." (v24.4) |
| implicit declaration `x = 0` | `var x = 0` | `DEPRECATED` | "All variable declarations should use `var`. Implicit variable declarations are deprecated, and now warn with a fix-it that inserts `var`." Warning text: `implicit declaration of 'x' is deprecated; add 'var' before the name`. |
| `read` (argument and closure-capture convention) | `imm` | `DEPRECATED` | "`imm` is now the preferred spelling for the `read` argument and closure-capture convention. `read` still works but will soon be deprecated." |
| `owned` keyword | `var` (params) or `deinit` (`__deinit__`/move args) | `REMOVED` | "The `owned` keyword has been removed. Use `var` for parameters or `deinit` for `__moveinit__`/`__del__` arguments as appropriate." (v0.26.2) |
| bare `**kwargs` | `var **kwargs` | `REMOVED` (error) | "A bare `**kwargs` is now an error; write `var **kwargs` (a fix-it inserts it) in function declarations and function types alike." |
| `escaping` effect on closures | explicit capture list `{...}` | `REMOVED` | "The `escaping` function effect is no longer supported." (v1.0.0b1) |
| `constrained[cond, msg]()` | `comptime assert cond, msg` | `REMOVED` | "The `constrained[cond, msg]()` function. Use `comptime assert cond, msg` instead." (v1.0.0b2) |
| `where` inside a parameter list (`[x: Int where x > 0]`) | trailing `where` after the signature | `REMOVED` | "`where` clauses inside a parameter list ... are no longer supported ... Use a trailing `where` clause after the signature instead." |
| `alias` | `comptime` | `DEPRECATED` | The compiler warns on `alias` and suggests `comptime`. (v0.26.1) Note: `alias` is not on the official keyword list — a documentation gap flagged in the [`intro/stability`](../intro/stability.md) chapter. |
| method `self: Foo[Int]` | `self` with a `where Self.T == Int` clause | `REMOVED` | "Method `self` parameters must now have type `Self`; switch a custom `self` type to a `where` clause." |
| overloads differing only in convention (`imm` vs `mut`) | one overload; distinguish another way | `REMOVED` | "Mojo now rejects function overloads that differ only in argument convention." |
| reserved words as free-function names (`class`, `del`, `match`, `yield`) | escaped identifier `` `match` `` | `REMOVED` | "You can no longer use predefined and reserved words ... as the name of a free function." |
| newline in the middle of a `def`/`struct`/`trait`/`comptime` header or an `import` | keep the header on one line | `REMOVED` | "The compiler now rejects newlines in the middle of certain statements." |

### Pointers and memory

`Pointer` and `UnsafePointer` were unified into a single **`Pointer`** type;
the unsafe operations are now spelled with an `unsafe_` prefix instead of being
carried by an unsafe *type*. Official summary: "The `UnsafePointer` name and the
unprefixed unsafe operations are deprecated." The two old types share layout and
convert implicitly, so most code compiles but warns.

**Alias renames** (all old names deprecated):

| OLD (pre-1.0) | NEW (1.x) | STATUS |
|---------------|-----------|--------|
| `UnsafePointer` | `Pointer` | `DEPRECATED` |
| `MutUnsafePointer` | `MutPointer` | `DEPRECATED` |
| `ImmUnsafePointer`, `ImmutUnsafePointer` | `ImmPointer` | `DEPRECATED` |
| `OptionalUnsafePointer` | `OptionalPointer` | `DEPRECATED` |
| `Pointer`'s `type` parameter | `Pointer[...]`'s `T` parameter | `DEPRECATED` |

### APIs removed outright in 1.0

These have **no** old→new alias. Migration is manual.

| REMOVED | Replacement / guidance |
|---------|-----------------------|
| `DType.invalid` | `Optional[DType]` |
| positional indexing on `StringLiteral` (`literal[i]`) | the `[byte=]`, `[codepoint=]`, `[grapheme=]` keyword accessors |
| static `String.write()` methods | the equivalent `String()` constructor (member `write()` is unchanged) |

## Old and new code side by side

Each pair shows a pre-1.0 block and its 1.x replacement. The pre-1.0 blocks are
**not** valid 1.x code.

### 1. A small function: `fn` → `def`

```mojo
# PRE-1.0 — does not compile in 1.x (`fn` is an error as of v1.0.0b2)
fn greet(name: String) -> String:
    return "Hello, " + name
```

```mojo
# 1.x
def greet(name: String) -> String:
    return "Hello, " + name
```

### 2. A struct with a destructor: `__del__`/`owned`/`@value` → `__deinit__`/`deinit`

```mojo
# PRE-1.0 — `@value` is removed, `owned` is removed, `__del__` is deprecated
@value
struct Handle:
    var fd: Int

    fn __del__(owned self):
        close(self.fd)
```

```mojo
# 1.x — write the initializer decorator you need, and name the destructor `__deinit__`
@fieldwise_init
struct Handle(Deinitable):
    var fd: Int

    def __deinit__(deinit self):
        close(self.fd)
```

A struct is implicitly `Deinitable`; the explicit conformance above is optional
and shown for clarity. For a type that must be destroyed explicitly, the
current form is `Deinitable where False` together with
`@explicit_destroy("...")`, not the old `@explicit_destroy` opt-out.

### 3. A pointer use: unsafe type + unprefixed ops → unified `Pointer` + `unsafe_` ops

```mojo
# PRE-1.0 — `UnsafePointer` and the bare subscript are deprecated in 1.x
fn sum4(ptr: UnsafePointer[Int]) -> Int:
    var total = 0
    for i in range(4):
        total += ptr[i]        # unchecked offset, previously implicit
    return total
```

```mojo
# 1.x — one `Pointer` type; the unsafe offset is written down
def sum4(ptr: Pointer[Int]) -> Int:
    var total = 0
    for i in range(4):
        total += ptr[unsafe_offset=i]
    return total
```

The point of the unification is the safety marker, not the name: the type is now
the same `Pointer` for safe and unsafe uses, and each individually unsafe
operation is spelled `unsafe_`.

### 4. An argument convention: `read`/`owned` → `imm`/`var`

```mojo
# PRE-1.0 — `read` is deprecated (use `imm`); `owned` is removed (use `var`)
def scan(read data: Span[Int], owned scratch: List[Int]) -> Int:
    ...
```

```mojo
# 1.x
def scan(imm data: Span[Int], var scratch: List[Int]) -> Int:
    ...
```

### 5. A `**kwargs` function: bare → `var **kwargs`

```mojo
# PRE-1.0 — a bare `**kwargs` is an error in 1.x
def configure(**kwargs: Int):
    for item in kwargs.items():
        print(item.key, "=", item.value)
```

```mojo
# 1.x — `var` is the only supported convention, and it is now required
def configure(var **kwargs: Int):
    for item in kwargs.items():
        print(item.key, "=", item.value)
```

The semantics are unchanged: `var` was already the only convention the compiler
supported, it was just applied silently before.

### 6. A collection type annotation: `InlineArray`/`StringSlice`/`.size` → `Array`/`StringSpan`/`.length`

```mojo
# PRE-1.0 — all three spellings are deprecated in 1.x
var buffer: InlineArray[UInt8, 16]
var view: StringSlice
var n = buffer.size
```

```mojo
# 1.x
var buffer: Array[UInt8, 16]
var view: StringSpan
var n = len(buffer)
```

Also note the newer idiomatic construction: a list expression now builds an
`Array`, not a `List` — `var x = [1, 2, 3]` has type `Array[Int, 3]` — which
removes an implicit heap allocation.

## What shipped with a safety net

The official promise is that "nearly every breaking change ships with a
deprecated alias and a compiler fix-it, so migration is mechanical." That means
a lot of 0.x code still **compiles** on 1.0.0, with warnings. The net is real,
but it is only a migration aid:

- **Compiler fix-its** are documented for: `fn` → `def` (warning at b1, error at
  b2); `__del__()` → `__deinit__()` ("emits a deprecation warning with a fix-it
  to rename it"); implicit var-less declaration ("warn with a fix-it that
  inserts `var`"); bare `**kwargs` → `var **kwargs` ("a fix-it inserts it"); and
  `@unavailable(use=symbol)`, whose error includes a fix-it renaming the call.
  Fix-its can be applied automatically with `--experimental-fixit`, or exported
  as YAML for `clang-apply-replacements` with `--experimental-export-fixit`
  (introduced in v0.25.7/v0.26.1).
- **Deprecated aliases that keep old code compiling** include: `InlineArray`
  (comptime alias) and `.size` as an alias for `.length`; `StringSlice`,
  `MutStringSlice`, `ImmStringSlice`; `ImplicitlyDestructible` and
  `ImplicitlyDeletable`; the unprefixed pointer operations (which still work but
  are hidden from generated docs and warn); `Variant.take`/`unsafe_take`;
  `List.steal_data()` and `OwnedPointer.steal_data()`; `as_immutable()`,
  `get_immutable()`, `OwnedPointer.take()`, `StaticConstantOrigin`; `read` (still
  works, "will soon be deprecated"); and `SIMDSize` as an alias for
  `SIMDLength`.
- **Breaking changes with no alias or fix-it** (handle these by hand): implicit
  `std` imports (error), negative indexing (compile-time error), method `self`
  must be `Self`, overloads differing only in convention, struct fields hiding
  `UnsafeAnyOrigin`, reserved words as free-function names, newline rejections,
  `DType.invalid`, positional `StringLiteral` indexing, static `String.write()`,
  and `trait_downcast_var()`.

**Do not rely on this safety net.** Three reasons: the warnings are slated to
become errors (`fn` already did within the 1.0.0 betas); some old spellings are
hidden from generated docs even while they compile, so the documentation no
longer teaches them; and the aliases exist only "for the time being". Migrate
to the new spelling rather than silencing the warning.

## What is now idiomatic in 1.x

These are style and idiom changes to apply even where the old form still
compiles. All from the 1.0.0 release notes unless noted.

- **Use `def` for every function declaration.** `fn` is a historical spelling
  only; the manual now carries the caution that `fn` is deprecated.
  <https://mojolang.org/docs/manual/functions/>
- **Always declare variables with an explicit binding.** "All variable
  declarations should use `var`."
- **Spell out mutability and ownership** instead of relying on silent defaults
  ("Explicit over implicit").
- **Write `imm` rather than `read`** for read-only argument and closure-capture
  conventions.
- **Use the `length` vocabulary, not `size`** (`Array[T, length]`,
  `SIMD[dtype, length]`, `List.resize(new_length=, fill=)`).
- **Prefer `Array` over `List`** for fixed-size values; a list expression now
  constructs an `Array` by default, eliminating an implicit heap allocation.
- **Use the unified safe `Pointer`** and put `unsafe_` at the point of
  unsafety, rather than choosing an unsafe pointer *type*.
- **Copy explicitly.** Prefer `.copy()` or the `^` transfer; only
  `ImplicitlyCopyable` types copy implicitly. `Array`, `List` and the other
  containers are explicitly copyable only.
- **Use closure capture lists** (`def f() {imm x}:`) instead of legacy
  `@parameter` / `@__copy_capture` closures, which are deprecated and should not
  be used in new code.
- **Name the destructor `__deinit__`** and use `deinit self`; use
  `Deinitable where False` plus `@explicit_destroy("message")` for linear types.
- **Use fixed-width types (`Int32`) at the GPU boundary.** `Int`/`UInt` are
  platform-sized index types and no longer `DevicePassable`.
- **Import from `max` for accelerator APIs** now that GPU stdlib APIs moved
  there, and use fully qualified standard-library imports.
- **Model nullable pointers with `Optional[Pointer[...]]`**, not a null default
  constructor.
- **Iterate strings knowing the unit is grapheme clusters**, and use
  `codepoints()`/`bytes()` when you need a lower-level view.
- **Avoid negative indexing**; write `x[len(x) - 1]`, and guard the empty case
  (for example `lst[: max(len(lst) - 1, 0)]`).
- **Prefer `StringSpan` over `StringSlice`**, `Deinitable` over
  `ImplicitlyDestructible`, `Ordering` over `Consistency` — the consolidated
  names, not the compatibility aliases.

## Open questions

- The official manual still contains prose that calls a function "an `fn`
  function" and some current pages still show `UnsafePointer`, even though both
  are superseded in 1.0.0. Treat any `fn` or `UnsafePointer` outside this
  chapter's tables as documentation lag, not current syntax. The release notes
  are the authority: <https://mojolang.org/releases/v1.0.0b2/>.
- The release notes do not give a single consolidated removal schedule for the
  deprecated aliases. "Will be removed in a future release" is the strongest
  official statement available; do not assume a date.
- `Ordering`/`Consistency` and the `@register_passable`/`RegisterPassable`
  changes landed in v1.0.0b1, and init unification in v0.26.2, so pre-1.0 code
  from *different* 0.x versions needs different subsets of these tables. This
  page is the 1.0.0 end state; use it as the goal, not as a per-0.x delta.
